# PR 검토 후 병합

이 스킬은 이화 발주 시스템 저장소(`EWhaFood/EWha_OrderingSystem`)에서 PR이나 feature 브랜치를 main에 합치기 전에, 이 프로젝트에서 실제로 사고가 나기 쉬운 지점을 집중 점검하기 위한 것이다. 범용 코드 리뷰가 아니라 **이 스택(Firebase Firestore + Cloud Functions + Flutter, 운영자/거래처 이중 역할)에 특화된 검토**가 목적이다.

병합은 되돌리기 어렵고 팀 전체에 영향을 주므로, 검토 없이 합치지 않는다. 반대로 사소한 스타일 지적으로 병합을 막지도 않는다 — 실제 위험(보안·데이터 격리·빌드 깨짐)과 개선 제안(리팩토링)을 구분해서 보고한다.

## 워크플로우

순서대로 진행한다. 각 단계는 앞 단계의 결과에 의존한다.

### 1. 변경 파악

먼저 무엇이 바뀌는지 정확히 본다. 파일 목록만 보지 말고 실제 diff를 읽는다.

```bash
gh pr view <번호> --json title,body,files          # gh 있을 때
gh pr diff <번호>
# gh 없으면:
git fetch origin && git diff origin/main...<브랜치>
```

바뀐 파일을 유형별로 분류한다 — `firestore.rules` / `functions/` / `lib/` / 설정 파일. 유형마다 봐야 할 위험이 다르다.

### 2. 보안 규칙 검토 (최우선)

이 프로젝트에서 가장 사고가 잦은 영역이다. 아래 "보안 체크리스트"를 항목별로 확인한다. 하나라도 걸리면 **병합 보류** 사유다.

### 3. 리팩토링·품질 검토

"리팩토링 체크리스트"를 확인한다. 여기서 나온 것은 대개 **개선 제안**이지 병합 차단 사유가 아니다 — 단, 명백한 버그나 규칙 위반은 차단으로 올린다.

### 4. 검토 리포트 작성

아래 "리포트 형식"으로 결과를 정리한다. 판정(병합 가능 / 보류)과 근거를 명확히 한다.

### 5. 병합 (승인 후)

**보류 사유가 하나도 없을 때만** 병합을 제안한다. 병합은 사용자가 명시적으로 "병합해"라고 확인한 뒤에만 실행한다 — 검토 통과가 곧 병합 승인은 아니다.

```bash
gh pr merge <번호> --squash --delete-branch    # 기본: squash 병합 + 브랜치 정리
```

보류 사유가 있으면 병합하지 말고, 무엇을 고쳐야 하는지 안내한다.

## 보안 체크리스트

이 프로젝트의 구조상 아래가 뚫리면 거래처 데이터 유출이나 권한 우회로 직결된다. 각 항목을 실제 코드와 대조해 확인한다.

- **시크릿 하드코딩 금지**: 카페24 `Client Secret`·Access/Refresh Token, 기타 API 키가 `lib/`(앱 코드)나 커밋된 파일에 문자열로 들어가면 안 된다. 이런 값은 Functions 환경/Secret Manager·Firestore의 차단된 컬렉션에만 존재해야 한다. 앱은 절대 카페24를 직접 호출하지 않는다(토큰이 클라이언트로 새면 유출). `grep -rniE "secret|token|apikey|client_secret" lib/ functions/src/`로 훑어본다.
- **google-services.json 외 민감정보**: `google-services.json`·`firebase_options.dart`의 클라이언트 키는 규칙으로 보호되므로 커밋돼도 되지만, 서비스 계정 JSON(`*-adminsdk-*.json`)이나 `.env`가 커밋되면 안 된다.
- **Firestore 규칙 커버리지**: `lib/`에 새 컬렉션을 읽거나 쓰는 코드가 생겼다면 `firestore.rules`에 그 컬렉션 규칙이 있는지 확인한다. 규칙 없는 컬렉션은 기본 차단이라 런타임 에러가 나거나, 반대로 임시로 열어둔 규칙이 남아 있으면 유출된다.
- **역할 격리 유지**: 거래처(partner)는 자기 `partnerId` 문서만 read/create 가능하고, 주문 상태 변경(update)과 partners/products 쓰기는 운영자(operator)만 가능해야 한다. 규칙 변경 diff에서 이 격리가 느슨해지지 않았는지 본다. 특히 `allow read/write: if true` 또는 인증만 확인하고 소유권/역할을 안 보는 규칙을 경계한다.
- **role·partnerId 위조 방지**: `users` 문서의 `role`·`partnerId`는 클라이언트가 못 바꿔야 한다(Functions 전용). 앱 코드가 이 필드를 write하려 하면 권한 상승 위험이다.
- **주문 생성 제약**: 거래처의 orders create는 `source='app'`·`status='new'`·본인 `partnerId`로만 제한돼야 한다. 규칙에서 이 조건이 빠지면 거래처가 임의 상태·타 거래처 주문을 만들 수 있다.

## 리팩토링 체크리스트

품질·유지보수 관점. 대부분 제안 수준이지만, 팀 컨벤션(`CLAUDE.md`) 위반은 일관성을 위해 짚는다.

- **함수 길이**: 함수당 최대 50줄(프로젝트 규칙). 넘으면 분리 제안. 특히 `build()`나 `fromDoc()`이 비대해지기 쉽다.
- **타입 힌트**: 모든 선언에 타입 명시(프로젝트 규칙). Dart는 `var`/추론 대신 명시 타입, 함수 반환/파라미터 타입 필수.
- **스키마 일관성**: 모델(`lib/core/models/`) 필드가 `firestore.rules`·실제 Firestore 문서 구조와 일치하는지. `source`/`status` 같은 값은 `order_status.dart`의 enum을 쓰고 문자열 리터럴을 흩뿌리지 않는다.
- **중복**: 여러 화면이 같은 Firestore 쿼리·직렬화를 복붙하고 있으면 공통 함수로 추출 제안.
- **Functions 규칙**: 리전이 `asia-northeast3`인지, 외부 호출(카페24)에 에러 처리·재시도가 있는지, `onRequest` 함수가 의도치 않게 public이 아닌지.
- **불필요 잔재**: 디버그용 `print`/`console.log`, 주석 처리된 코드, 임시 우회(예: `android.overridePathCheck`가 더 이상 필요 없는데 남아 있는 경우) 정리 제안.

## 리포트 형식

검토 결과는 항상 이 구조로 정리한다. 판정을 맨 위에 둬서 병합 가능 여부가 한눈에 보이게 한다.

```
## 검토 결과: <PR 제목> (#<번호>)

**판정: 병합 가능 / 보류**

### 🔴 보류 사유 (있으면 병합 불가)
- [파일:줄] 무엇이 왜 위험한지, 어떻게 고칠지

### 🟡 개선 제안 (병합은 가능, 후속 처리 권장)
- [파일:줄] 제안 내용

### ✅ 확인한 것
- 보안: 역할 격리·시크릿·규칙 커버리지 점검 결과
- 품질: 규칙 준수 여부
```

보류 사유가 없으면 🔴 섹션은 "없음"으로 명시한다 — 검토를 건너뛴 게 아니라 통과했다는 걸 분명히 하기 위해서다.

## 참고

- 더 깊은 정적 분석이 필요하면 빌트인 `/security-review`(보안)·`/code-review`(정확성·품질)를 함께 돌려 교차 확인한다. 이 스킬은 그 위에 **이 프로젝트 특화 관점 + 병합 결정**을 얹는 역할이다.
- 검토 전 로컬에서 `dart analyze lib`와 `flutter build apk --debug`가 통과하는지 확인하면, 규칙 논리 외의 컴파일·빌드 문제를 미리 거른다.
